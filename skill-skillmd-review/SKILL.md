# Skill Skillmd Review

本 Skill 用于辅助修改 Codex skill 的 `SKILL.md`：把一个现有或草拟的 skill 指令文件改成更符合规范、更容易触发、更可执行、更可验证的版本。

核心目标是**帮助完成有效修改**。点评、逐行分析和方法总结用于定位问题、解释修改理由、降低误改风险。

## 适用场景

- 用户要求修改、优化、规范化或修复某个 `SKILL.md`。
- 用户指出 skill 定位、流程、触发描述、资源组织或验证规则存在问题。
- 用户要求审查某个 skill，并希望把结论落到可执行修改。
- 用户要求对比优秀 skill 的结构，并把可迁移经验补进目标 skill。

---

## 工作原则

1. 优先服务修改目标：用户要求改文件时，直接进入修订流程，不停留在评价。
2. 保留原始意图：先识别这个 skill 想解决的真实任务，再改表达、流程和边界。
3. 修改要可执行：每条指令都应帮助未来 Codex 判断何时使用、如何行动、如何验证。
4. 规范优先：`frontmatter`、触发描述、正文结构、资源引用和交付规则必须符合 Codex skill 约定。
5. 点评服务于修改：只有在需要解释问题、比较方案或用户要求审查时，才输出详细点评。
6. 控制文件范围：只在用户要求或规范需要时创建 README、变更日志、外部说明文档。

---

## 默认工作流

```text
Phase 1   读取和理解
   1.1  确认目标 SKILL.md
   1.2  读取全文和相关元数据
   1.3  识别 skill 的目标、触发场景、输入、输出和边界
   ▼
Phase 2   诊断修改点
   2.1  检查 frontmatter 是否规范
   2.2  检查 description 是否能准确触发
   2.3  检查正文是否可执行、可验证、不过度冗长
   2.4  检查资源目录和引用是否必要且清晰
   2.5  检查 SKILL.md 是否超过 500 行
   2.6  对齐规范化结构和流程
   ▼
Phase 3   实施修改
   3.1  在同级 cache 目录备份修改前的 SKILL.md
   3.2  保留有效内容
   3.3  删除或压缩偏离目标的说明
   3.4  重写目标、边界、流程、验证和交付规则
   3.5  必要时同步 agents/openai.yaml 等相关元数据
   ▼
Phase 4   验证和交付
   4.1  做结构和规范检查
   4.2  按失败项修复后重新检查
   4.3  说明改了什么、为什么改
   4.4  如实说明未验证项或剩余风险
```

目标 skill 目录约定：

```text
<skill-folder>/
├── SKILL.md              # 必有，修改和审查的主入口
├── agents/openai.yaml    # 可选，UI 展示元数据；定位变化后检查是否同步
├── references/           # 可选，长细则、示例、规范和排错资料
├── scripts/              # 可选，稳定可重复的自动化或验证脚本
├── assets/               # 可选，模板、示例工程、媒体或可复制资源
└── cache/<YYYY-MM-DD>/   # 本 skill 修改前备份目录
    └── skill-<HHmmss>.md
```

## Phase 1 - 读取和理解

### 1.1 确认目标文件

优先读取用户指定的 `SKILL.md`。如果用户只给 skill 目录，默认读取该目录下的：

```text
SKILL.md
```

如果目录中不存在 `SKILL.md`，直接说明缺失，并要求用户提供正确的 skill 入口。

### 1.2 读取相关文件

至少读取目标 `SKILL.md`。按需读取：

| 文件或目录 | 何时读取 | 用途 |
|---|---|---|
| `agents/openai.yaml` | skill 定位、展示名称、短描述或默认提示变化时 | 判断 UI 元数据是否需要同步 |
| `references/` | 正文引用参考资料，或需要把长细则下沉时 | 检查按需读取说明和内容归属 |
| `scripts/` | 正文要求运行脚本、验证脚本或脚本化重复步骤时 | 检查命令、脚本职责和验证路径 |
| `assets/` | skill 产出依赖模板、示例工程、媒体或可复制资源时 | 检查资源是否存在且引用准确 |

只读取本次修改所需的文件。

### 1.3 识别真实任务

修改前先用一句话概括该 skill 的真实用途：

```text
这个 skill 用于 <触发场景>，把 <输入> 处理成 <产出>。
```

如果当前正文和用户描述冲突，以用户最新描述为准，并把正文改到一致。

## Phase 2 - 诊断修改点

### 2.1 frontmatter

检查并修复：

- `name` 必须存在，使用小写字母、数字和短横线。
- `description` 必须存在，并写清何时触发、处理什么输入、产出什么结果、关键边界是什么。
- YAML frontmatter 只保留必要字段。
- `description` 应写出具体触发场景、输入、输出和边界。

`description` 是触发入口。正文中的“何时使用本 Skill”不能替代它。

### 2.2 目标和边界

检查并修复：

- 开头是否快速说明该 skill 的真实作用。
- 是否区分“核心目标”和“辅助方法”。
- 是否说明任务边界和排除场景，降低误触发或跑偏风险。
- 是否明确最终产出是文件修改、修订建议、验证结果，还是三者组合。

当用户指出定位错误时，优先重写开头目标、`description` 和流程总览。

### 2.3 工作流

检查并修复：

- 是否按读取、诊断、修改、验证、交付组织。
- 是否有清晰的阶段总览，让读者先看到全流程。
- 是否明确工作目录、关键文件和产出物职责。
- 是否设置必要 checkpoint，并说明停下来的条件和用户需要确认的内容。
- 是否能指导 Codex 在用户要求“直接改”时动手修改。
- 是否把用户确认点放在真正高风险的位置。
- 是否说明信息不足、验证失败、文件缺失时怎么处理。

流程应该让未来 Codex 知道下一步该做什么，并把评价结论转化为修改动作。

### 2.4 资源组织

检查并修复：

- 主 `SKILL.md` 是否只保留核心流程和决策规则。
- 详细规范、长示例、领域资料是否适合放进 `references/`。
- 重复、稳定、容易出错的步骤是否适合放进 `scripts/`。
- 模板、示例工程、媒体或可复制素材是否适合放进 `assets/`。
- 正文中对资源的引用是否说明“何时读取”和“读取后做什么”。

资源必须服务实际执行；空资源目录说明应删除。

### 2.5 长度和渐进披露

检查并修复：

- 统计 `SKILL.md` 行数，目标是保持在 500 行以内。
- 如果 `SKILL.md` 超过 500 行，将细则、长示例、详细规范、场景矩阵、排错说明拆分到 `references/`。
- 主 `SKILL.md` 保留核心流程、关键决策点、资源索引和按需读取规则。
- 拆分到 `references/` 的内容必须从主文件直接链接，并说明何时读取、读取后用于什么决策或动作。
- 拆分后检查主文件和 reference 文件之间没有重复维护同一事实。

可使用的资源指引格式：

```markdown
详细 <主题> 规则见 `references/<topic>.md`。当用户请求 <场景> 或需要判断 <条件> 时读取；读取后用于 <动作>。
```

### 2.6 规范化结构对齐

审查和修改复杂 skill 时，优先对齐这种结构骨架：

1. `frontmatter`：`name` 和可触发的 `description`。
2. 一句话目标：说明输入、处理方式和产出物。
3. 适用场景或触发场景：列出用户自然语言请求类型。
4. 工作流总览：用阶段图展示主路径、checkpoint 和可选分支。
5. 工作目录约定：用目录树说明关键文件和产物位置。
6. 唯一真相源：复杂任务必须指定哪个文件决定关键事实，其他文件如何与它保持一致。
7. 硬性自检协议：每个关键产物完成后先自检、修复，再汇报或推进。
8. 阶段文件读取指南：用表格说明每个阶段必读文件、按需读取文件和读取目的。
9. 分阶段执行规则：每个 Phase 说明输入、动作、产出、停止条件。
10. 常见反馈速查：把用户反馈映射到修改层级和最小修改动作。
11. 相关资源索引：按“何时读”标注 `references/`、`scripts/`、`assets/` 或其他资源目录。

从优秀 skill 中可迁移的优点：

- 先给全局流程，再展开细节，降低长文档迷路风险。
- 用 checkpoint 把高风险决策显式化，减少擅自推进。
- 用工作目录树和唯一真相源控制多文件一致性。
- 用“硬性自检 → 修复 → 汇报”保证验证结果真的进入产物。
- 用阶段读取表实现渐进披露，减少一次性加载所有资源。
- 用资源索引说明何时读取、读后做什么，保证资源可发现且按需使用。

对齐时按目标 skill 的复杂度裁剪。轻量 skill 可保留最小骨架；涉及多阶段、多文件、多资源或用户验收的 skill，应补齐目录约定、唯一真相源、checkpoint、自检协议和资源索引。

### 2.7 验证和失败处理

检查并修复：

- 是否有修改后的自检清单。
- 是否要求关键产物完成后先自检、按失败项修复，再汇报或进入下一步。
- 是否说明可用的验证命令或结构检查方式。
- 是否要求失败后先修复，再交付。
- 是否要求无法验证时如实说明。

高质量 skill 不只告诉 Codex 怎么写，还要告诉 Codex 怎么判断写对了。

### 2.8 表达审查

检查并修复：

- 将“不是 X，而是 Y”“不要 X，而要 Y”“不要只 X，而要 Y”这类否定对照句，改写成直接的正向目标句。
- 用“要 Y”“优先 Y”“核心目标是 Y”“X 用于 Y”表达真实要求。
- 将否定内容保留为边界、风险或排除场景时，必须说明具体触发条件和处理动作。

示例：

```text
原写法：核心不是写点评报告，而是帮助完成有效修改。
推荐写法：核心目标是帮助完成有效修改。
```

## Phase 3 - 实施修改

### 3.1 修改前备份

用户要求直接修改 `SKILL.md` 时，先在目标 `SKILL.md` 同级工作目录创建修改前备份，再编辑原文件。

备份目录结构：

```text
cache/<YYYY-MM-DD>/skill-<HHmmss>.md
```

日期目录使用系统当前日期，格式固定为：

```text
YYYY-MM-DD
```

备份文件名使用系统当前时间，推荐使用不含冒号的时间格式，保证文件名可跨平台保存：

```text
skill-HHmmss.md
```

示例：

```text
cache/2026-05-17/skill-212208.md
```

备份内容必须是修改前的目标 `SKILL.md` 原文。备份完成后再进入正文修改。

### 3.2 修改策略

用户要求直接修改时：

1. 读取当前文件。
2. 按 `cache/<YYYY-MM-DD>/skill-<HHmmss>.md` 保存修改前备份。
3. 识别必须保留的目标、术语、资源路径和执行约束。
4. 删除偏离目标的长篇点评、泛化方法论和重复段落。
5. 重写触发描述、目标段、工作流、验证和交付规则。
6. 如果正文超过 500 行，将细则拆分到 `references/`，并在主文件保留按需读取指引。
7. 对复杂 skill 补齐工作目录约定、唯一真相源、checkpoint、自检协议、阶段读取表和资源索引。
8. 保持 Markdown 结构清晰，把正文写成给 Codex 执行的操作指令。
9. 修改后检查 `agents/openai.yaml` 是否明显过期；如过期且修改范围允许，同步更新。

### 3.3 保留与删除

优先保留：

- 能提高触发准确率的描述。
- 能约束执行行为的边界。
- 能复用的工作流、检查点、验证规则。
- 工作目录树、唯一真相源、硬性自检协议和阶段读取表。
- 真实存在且会被使用的资源路径。
- 指向 `references/` 的按需读取说明。

优先删除或压缩：

- 空泛评价标准。
- 与当前 skill 目标冲突的“核心产出”描述。
- 缺少下一步行动指导的大段抽象方法论。
- 重复出现的检查项。
- 用户没有要求、也不会被 Codex 使用的说明性文档。
- 已拆分到 `references/` 后仍在主文件重复维护的细则。

### 3.4 点评的使用方式

点评只在这些场景输出：

- 用户明确要求审查、逐行分析或解释修改理由。
- 修改前需要指出高风险冲突，降低误改风险。
- 修改后需要说明关键变更为什么必要。

点评应服务具体修改，并落到文件变更、修改建议或验证结论。

可使用的简短格式：

```markdown
**问题**
- <位置或段落>：<问题 + 影响>

**修改**
- <已改内容或建议改法>

**理由**
- <为什么这样更符合 skill 规范或更有效>
```

### 3.5 直接修订输出

当用户要求“改一下”“优化这个 SKILL.md”“按我的定位重写”时，默认直接编辑文件。最终回复只需说明：

- 修改了哪些区域。
- 修改前备份路径。
- 现在的定位是什么。
- 做过哪些检查。
- 是否还有未处理风险。

最终回复保持摘要式交付；只有用户要求时才粘贴完整 `SKILL.md`。

## Phase 4 - 验证和交付

### 4.1 硬性自检协议

修改完成后必须先自检。发现失败项时，先修复文件，再重新检查；最终回复汇报修复后的结果。

自检顺序：

1. 检查 frontmatter、目标、流程、资源、长度、表达和交付规则。
2. 检查修改前备份是否存在。
3. 检查 `agents/openai.yaml` 是否因定位变化而过期。
4. 运行可用的验证脚本；无法运行时说明原因并完成手动结构检查。

### 4.2 结构自检

修改后至少检查：

| 类别 | 检查问题 |
|---|---|
| 触发 | `description` 是否写清使用场景、输入、输出和边界？ |
| 规范 | frontmatter 是否只有必要字段，且 YAML 格式有效？ |
| 目标 | 开头是否直接说明真实作用？ |
| 边界 | 是否说明该做什么、不该做什么？ |
| 流程 | 是否能指导 Codex 从读取走到修改和验证？ |
| 结构 | 是否按目标、场景、总览、文件约定、阶段规则、验证、资源索引组织？ |
| Checkpoint | 高风险决策前是否有明确暂停点和用户确认内容？ |
| 唯一真相源 | 多文件任务是否指定关键事实来源，并说明同步规则？ |
| 备份 | 修改前是否已保存到 `cache/<YYYY-MM-DD>/skill-<HHmmss>.md`？ |
| 产出 | 是否明确最终交付是修改、建议、验证结果或组合？ |
| 资源 | 引用的 `references/`、`scripts/`、`assets/` 是否必要且可定位？ |
| 长度 | `SKILL.md` 是否保持在 500 行以内，超出时是否已拆分细则到 `references/`？ |
| 按需读取 | 主文件是否保留了 reference 资源指引、读取条件和使用目的？ |
| 验证 | 是否说明如何检查修改有效，并要求失败项先修复再汇报？ |
| 表达 | 是否把否定对照句改成了直接的正向目标句？ |
| 简洁 | 是否删除了不会影响执行的冗余解释？ |

### 4.3 可运行验证

如果 skill-creator 的验证脚本可用，优先运行：

```bash
scripts/quick_validate.py <path/to/skill-folder>
```

如果当前环境没有该脚本或无法运行，至少做人工结构检查，并在最终回复中说明未运行脚本验证。

### 4.4 交付规则

最终回复使用用户的语言。用户使用中文时，用中文回复。

交付时保持简洁，包含：

```markdown
已修改 `<path>`。

主要变化：
- <变化 1>
- <变化 2>
- <变化 3>

备份：
- <cache 路径>

验证：
- <已运行或已检查的项目>
```

如果没有修改文件，只输出审查建议时，要明确说明“未改文件”。

## 常见用户意图映射

| 用户说法 | 默认行动 |
|---|---|
| “修改 SKILL.md” | 先备份到同级 `cache` 目录，再编辑文件，最后做结构检查 |
| “这个定位不对” | 优先改 `description`、开头目标和流程总览 |
| “点评太多” | 删除审查报告导向内容，改成执行型修改流程 |
| “帮我看看哪里有问题” | 输出诊断；如问题明确且用户没有禁止修改，可提出或实施修订 |
| “按规范整理” | 检查 frontmatter、正文结构、资源引用和验证规则，并直接修订 |
| “逐行分析” | 生成带定位的分析，但仍把结论落到可执行修改建议 |

---

## 语言规则

当用户使用中文交流时，使用中文回应。代码标识符、命令、路径、API 名称和错误信息保持原文。

修改建议和交付说明要具体、直接、可执行。用文件内容或 skill 规范支撑每个重要判断。
