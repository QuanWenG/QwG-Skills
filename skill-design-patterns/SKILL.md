# Skill Design Patterns

## 工作流程

1. 先识别当前代码任务的变化点、稳定点、职责边界和依赖方向，避免为了套用模式而引入不必要抽象。
2. 先查阅下方“设计模式速查表”，根据问题形态选择 0 到 3 个候选设计模式，或选择更轻量的 SOLID 原则、组合、接口隔离、依赖倒置。
3. 一旦出现候选模式，必须到 `assets/design-patterns/` 下打开对应模式文档细读，再判断是否采用；不要只凭模式名称直接套用。
4. 在实现前简要说明采用或不采用某个模式的理由，重点关注高内聚、低耦合、可测试性、可扩展性和现有代码风格一致性。
5. 编码时优先使用项目已有抽象、命名和模块边界；新增接口、工厂、策略、适配器、装饰器、观察者等结构必须服务于真实复杂度。
6. 完成后检查是否降低了调用方复杂度、隔离了变化点、避免了循环依赖，并补充与风险匹配的测试。

## 设计模式速查表

使用方法：

1. 先匹配“典型问题形态”，找到候选模式。
2. 到 `assets/design-patterns/<分类>/<模式名>.md` 阅读详细内容。
3. 对照文档中的适用场景、不适用场景、代价与风险、检查清单，确认是否真的使用。
4. 如果模式会引入超过当前问题复杂度的抽象，优先使用简单函数、组合、接口、依赖注入或 SOLID 原则。

### 面向对象设计原则优先判断

| 问题形态 | 优先考虑 | 详细文档 |
| --- | --- | --- |
| 一个类/模块因为多种原因频繁变化，业务、存储、展示、通信混在一起 | 单一职责原则 SRP | `assets/design-patterns/面向对象设计原则/单一职责原则-SRP.md` |
| 新增同类功能总要修改旧分支、旧类或核心流程 | 开闭原则 OCP | `assets/design-patterns/面向对象设计原则/开闭原则-OCP.md` |
| 子类替换父类后调用方行为异常，或实现类通过抛异常禁用接口能力 | 里氏替换原则 LSP | `assets/design-patterns/面向对象设计原则/里氏替换原则-LSP.md` |
| 高层业务直接依赖数据库、HTTP SDK、文件系统、第三方服务等细节 | 依赖倒转原则 DIP | `assets/design-patterns/面向对象设计原则/依赖倒转原则-DIP.md` |
| 接口太大，实现类有空实现、无意义方法或“不支持”异常 | 接口隔离原则 ISP | `assets/design-patterns/面向对象设计原则/接口隔离原则-ISP.md` |
| 为了复用代码而继承，但语义上不是 is-a 关系 | 合成复用原则 CRP | `assets/design-patterns/面向对象设计原则/合成复用原则-CRP.md` |
| 调用方需要了解太多内部结构，出现很长的对象导航链 | 迪米特法则 LOD | `assets/design-patterns/面向对象设计原则/迪米特法则-LOD.md` |

### 创建型模式

| 典型问题形态 | 候选模式 | 什么时候优先看它 | 详细文档 |
| --- | --- | --- | --- |
| 应用或容器范围内确实只需要一个共享实例，例如配置、日志门面、资源管理入口 | 单例模式 | 需要控制实例数量和访问点；同时确认全局状态、测试替换、生命周期风险可接受 | `assets/design-patterns/创建型设计模式/单例模式.md` |
| 调用方不应直接依赖具体产品类，创建哪种产品要延迟给子类或具体工厂决定 | 工厂方法模式 | 新增的是同一产品类型的不同实现，且创建逻辑需要隔离 | `assets/design-patterns/创建型设计模式/工厂方法模式.md` |
| 需要创建一族必须配套使用的对象，例如同一平台 UI、同一品牌产品族 | 抽象工厂模式 | 新增产品族较频繁，且必须保证产品族一致性 | `assets/design-patterns/创建型设计模式/抽象工厂模式.md` |
| 构造参数多、可选项多、构建步骤需要校验，或需要构建不可变复杂对象 | 建造者模式 | 对象创建过程比简单构造复杂，链式配置能明显提升可读性 | `assets/design-patterns/创建型设计模式/建造者模式.md` |
| 新对象和已有对象高度相似，创建成本高，希望复制后微调 | 原型模式 | 需要明确浅拷贝/深拷贝边界，且对象不含难复制资源 | `assets/design-patterns/创建型设计模式/原型模式.md` |

### 结构型模式

| 典型问题形态 | 候选模式 | 什么时候优先看它 | 详细文档 |
| --- | --- | --- | --- |
| 旧系统、第三方库或外部 SDK 的接口和当前客户端期望不一致 | 适配器模式 | 不能或不应修改旧接口，需要做参数、返回值、语义转换 | `assets/design-patterns/结构型设计模式/适配器模式.md` |
| 有两个独立变化维度，继承组合会导致类爆炸 | 桥接模式 | 抽象层和实现层都需要独立扩展，例如消息类型和发送渠道 | `assets/design-patterns/结构型设计模式/桥接模式.md` |
| 数据天然是树结构，客户端希望统一处理叶子和组合对象 | 组合模式 | 文件树、菜单树、组织架构、表达式树、组件树等整体-部分结构 | `assets/design-patterns/结构型设计模式/组合模式.md` |
| 需要在运行时动态叠加职责，避免继承组合爆炸 | 装饰模式 | 增强功能可一层层包装，且应保持原接口不变 | `assets/design-patterns/结构型设计模式/装饰模式.md` |
| 客户端完成一个用例需要调用一串复杂子系统 | 外观模式 | 需要提供稳定高层入口，降低调用方对内部流程的了解 | `assets/design-patterns/结构型设计模式/外观模式.md` |
| 存在大量细粒度相似对象，重复状态占用大量内存 | 享元模式 | 能清晰区分内部状态和外部状态，并能安全共享不可变状态 | `assets/design-patterns/结构型设计模式/享元模式.md` |
| 需要控制对目标对象的访问，例如权限、日志、缓存、远程调用、懒加载 | 代理模式 | 代理保持原接口，重点是访问控制或横切逻辑，而不是改变接口 | `assets/design-patterns/结构型设计模式/代理模式.md` |

### 行为型模式

| 典型问题形态 | 候选模式 | 什么时候优先看它 | 详细文档 |
| --- | --- | --- | --- |
| 一个请求可能由多个处理者按顺序尝试处理，处理链可配置 | 职责链模式 | 审批流、过滤器链、中间件链、校验链 | `assets/design-patterns/行为型设计模式/职责链模式.md` |
| 需要把一次操作封装为对象，以便排队、撤销、重做、日志、延迟执行 | 命令模式 | 触发者不应依赖执行者，操作本身有生命周期价值 | `assets/design-patterns/行为型设计模式/命令模式.md` |
| 需要遍历聚合对象但不暴露其内部结构 | 迭代器模式 | 集合结构复杂、遍历方式多样、需要语言迭代协议或自定义遍历 | `assets/design-patterns/行为型设计模式/迭代器模式.md` |
| 多个对象之间交互成网状，彼此直接引用过多 | 中介者模式 | 需要集中协调对象交互，例如 UI 控件联动、聊天室、工作流 | `assets/design-patterns/行为型设计模式/中介者模式.md` |
| 需要保存对象状态快照，并在之后恢复，同时不破坏封装 | 备忘录模式 | 撤销、重做、草稿、存档、事务回滚 | `assets/design-patterns/行为型设计模式/备忘录模式.md` |
| 一个对象变化后需要通知多个订阅者，订阅者集合可动态变化 | 观察者模式 | 事件系统、领域事件、UI 数据绑定、发布订阅 | `assets/design-patterns/行为型设计模式/观察者模式.md` |
| 对象行为随内部状态变化，大量方法都有状态分支 | 状态模式 | 状态转换规则复杂，新增状态会影响多处代码 | `assets/design-patterns/行为型设计模式/状态模式.md` |
| 存在一组可互换算法，运行时选择不同算法 | 策略模式 | 折扣、排序、路由、序列化、支付渠道等算法族 | `assets/design-patterns/行为型设计模式/策略模式.md` |
| 固定流程不变，局部步骤由子类实现 | 模板方法模式 | 框架控制执行顺序，子类只扩展特定步骤 | `assets/design-patterns/行为型设计模式/模板方法模式.md` |
| 需要解释小型稳定语法、规则表达式或表达式树 | 解释器模式 | 规则简单可组合；复杂语言解析应优先考虑解析器/规则引擎 | `assets/design-patterns/行为型设计模式/解释器模式.md` |
| 对象结构稳定，但经常新增跨元素操作 | 访问者模式 | AST、文档树、组合树上新增导出、统计、校验等操作 | `assets/design-patterns/行为型设计模式/访问者模式.md` |

## 采用前的否决条件

如果出现以下情况，默认不采用复杂设计模式，除非详细文档和当前代码上下文能证明收益大于成本：

- 只有一个实现，且短期没有明确变化点。
- 简单函数、数据结构、组合或依赖注入已经能清楚解决问题。
- 引入模式会让调用链更长、类型更多，但没有降低真实复杂度。
- 项目已有更简单、更一致的本地约定。
- 模式只是为了“看起来高级”，而不是隔离变化、降低耦合或提升测试性。

## 资源

- 只有当 Codex 需要按需读取详细资料时，才把内容放入 `references/`。
- 当任务重复、容易出错或需要稳定执行时，把自动化脚本放入 `scripts/`。
- 把可复制的模板、示例或媒体文件放入 `assets/`。

## 语言规则

当用户使用中文交流时，使用中文回应。代码标识符、命令、路径、API 名称和错误信息保持原文。生成面向用户的文档时，优先使用用户要求的语言；用户未说明时，沿用用户当前使用的语言。
