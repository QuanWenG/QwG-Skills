# 享元模式

## 摘要

享元模式通过共享相同对象来支持大量细粒度对象，减少内存占用。它的关键是区分内部状态和外部状态。

字符串常量池可以帮助理解共享思想，但完整享元模式通常还包含享元工厂，并把可共享状态从变化状态中拆开。

## 解决的问题

系统中存在大量相似对象，例如棋子、字符、地图瓦片、图标、粒子。如果每个对象都保存重复状态，会浪费内存。享元把可共享的内部状态集中复用，把变化的外部状态由调用方传入。

## 核心思想

内部状态存放在享元对象中，可共享且不可变；外部状态由客户端在使用时提供，例如坐标、颜色、上下文。

## 结构与角色

- Flyweight：享元接口。
- ConcreteFlyweight：保存内部状态。
- FlyweightFactory：缓存和复用享元。
- Client：保存或传入外部状态。

## 适用场景

- 对象数量非常大。
- 重复状态多。
- 内部状态可不可变化。
- 外部状态可以从对象中移出。

## 不适用场景

- 对象数量少。
- 对象状态高度个性化。
- 共享对象会引入复杂同步问题。

## 多语言实现

### Java

```java
import java.util.HashMap;
import java.util.Map;

record TreeType(String name, String color) {
    void draw(int x, int y) {}
}

final class TreeTypeFactory {
    private final Map<String, TreeType> cache = new HashMap<>();

    TreeType get(String name, String color) {
        String key = name + ":" + color;
        return cache.computeIfAbsent(key, k -> new TreeType(name, color));
    }
}
```

### C++

```cpp
struct Glyph { char ch; };
std::map<char, Glyph> cache;
Glyph& glyph(char c) { return cache.try_emplace(c, Glyph{c}).first->second; }
```

```go
type Glyph struct{ Ch rune }
```


### Python

```python
from functools import lru_cache


class Glyph:
    def __init__(self, font: str, char: str) -> None:
        self.font = font
        self.char = char


@lru_cache(maxsize=None)
def glyph(font: str, char: str) -> Glyph:
    return Glyph(font, char)
```

### TypeScript

```ts
class Icon {
  constructor(readonly name: string, readonly svg: string) {}
  render(x: number, y: number): void {}
}

class IconFactory {
  private cache = new Map<string, Icon>();

  get(name: string, svg: string): Icon {
    let icon = this.cache.get(name);
    if (!icon) {
      icon = new Icon(name, svg);
      this.cache.set(name, icon);
    }
    return icon;
  }
}
```

## 优点

- 显著减少重复对象内存。
- 共享不可变状态更安全。
- 创建成本降低。

## 代价与风险

- 需要拆分内部/外部状态。
- 缓存管理会增加复杂度。
- 共享可变对象会产生串扰。

## 常见误区

- 误区：享元就是对象池。
  正解：对象池复用实例生命周期，享元共享不可变内在状态。
- 误区：字符串常量池就是享元全部内容。
  正解：它只是一个典型例子。

## 和其他模式的关系

- 单例强调唯一实例，享元强调大量对象共享。
- 原型复制对象，享元共享对象。
- 工厂负责管理享元缓存。

## 检查清单

- 是否真的有大量重复对象？
- 内部状态是否不可变且可共享？
- 外部状态是否能由客户端传入？
- 缓存是否需要淘汰策略？
