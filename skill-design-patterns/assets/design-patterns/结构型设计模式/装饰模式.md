# 装饰模式

## 摘要

装饰模式在不修改原对象结构的情况下，动态地给对象添加职责。它通过包装对象实现功能叠加，是组合代替继承的典型模式。

原始笔记中的咖啡加奶加糖例子正确，但代码存在接口和关键字拼写问题；下面给出可编译版本。

## 解决的问题

如果用继承表示功能组合，会出现 `MilkCoffee`、`SugarCoffee`、`MilkSugarCoffee` 等组合爆炸。装饰器让功能可以按需叠加。

## 核心思想

组件和装饰器实现同一个接口。装饰器持有一个组件，在调用前后添加自己的逻辑，再委派给被包装对象。

## 结构与角色

- Component：公共接口。
- ConcreteComponent：原始对象。
- Decorator：抽象装饰器，持有 Component。
- ConcreteDecorator：具体增强功能。

## 适用场景

- 需要动态叠加功能。
- 功能组合很多，不想用继承爆炸。
- 不希望修改原类。
- 中间件、过滤器、流包装。

## 不适用场景

- 增强逻辑顺序极其复杂。
- 客户端必须知道所有具体装饰层。
- 对象身份敏感，包装后身份变化会造成问题。

## 多语言实现

### Java

```java
interface Coffee {
    String description();
    int cost();
}

final class SimpleCoffee implements Coffee {
    public String description() { return "coffee"; }
    public int cost() { return 10; }
}

abstract class CoffeeDecorator implements Coffee {
    protected final Coffee coffee;

    CoffeeDecorator(Coffee coffee) {
        this.coffee = coffee;
    }
}

final class MilkDecorator extends CoffeeDecorator {
    MilkDecorator(Coffee coffee) { super(coffee); }
    public String description() { return coffee.description() + ", milk"; }
    public int cost() { return coffee.cost() + 2; }
}
```

### C++

```cpp
struct Coffee { virtual int cost() = 0; virtual ~Coffee() = default; };
struct Milk : Coffee { Coffee& inner; Milk(Coffee& c): inner(c) {} int cost() override { return inner.cost() + 2; } };
```

### Go

```go
type Coffee interface{ Cost() int }
type Milk struct{ inner Coffee }
func (m Milk) Cost() int { return m.inner.Cost() + 2 }
```

### Kotlin

```kotlin
interface Coffee { fun cost(): Int }
class Milk(private val inner: Coffee) : Coffee { override fun cost() = inner.cost() + 2 }
```

### Python

```python
class Coffee:
    def description(self) -> str:
        return "coffee"

    def cost(self) -> int:
        return 10


class Milk:
    def __init__(self, coffee: Coffee) -> None:
        self._coffee = coffee

    def description(self) -> str:
        return self._coffee.description() + ", milk"

    def cost(self) -> int:
        return self._coffee.cost() + 2
```

### TypeScript

```ts
interface Handler {
  handle(input: string): string;
}

class BaseHandler implements Handler {
  handle(input: string): string { return input; }
}

class TrimDecorator implements Handler {
  constructor(private readonly next: Handler) {}
  handle(input: string): string {
    return this.next.handle(input.trim());
  }
}
```

## 优点

- 功能可动态组合。
- 避免继承层级爆炸。
- 单个装饰器职责清晰。

## 代价与风险

- 包装层多时调试困难。
- 装饰顺序可能影响结果。
- 需要保持接口一致。

## 常见误区

- 误区：装饰器就是继承扩展。
  正解：它的重点是运行时组合包装。
- 误区：装饰器可以随便改变接口。
  正解：装饰器应保持 Component 接口。

## 和其他模式的关系

- 代理也包装对象，但代理重点是访问控制；装饰重点是增加职责。
- 适配器改变接口，装饰器保持接口。
- CRP 是装饰模式的设计基础。

## 检查清单

- 是否需要动态叠加功能？
- 是否出现功能组合类爆炸？
- 装饰顺序是否明确？
- 装饰器是否保持原接口契约？
