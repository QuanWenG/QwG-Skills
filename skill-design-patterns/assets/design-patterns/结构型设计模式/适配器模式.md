# 适配器模式

## 摘要

适配器模式把一个类的接口转换成客户端期望的另一个接口，使原本接口不兼容的类可以协同工作。

对象适配器通过组合包装被适配者，适用面最广；类适配器通过继承适配，依赖语言支持多重继承，在 Java 中通常不典型。

## 解决的问题

旧系统、第三方 SDK、缓存服务、数据库服务经常有不同调用方式。客户端希望统一处理，但又不能或不应该修改这些已有类。适配器在中间做参数转换、返回值转换和语义对齐。

## 核心思想

客户端只依赖目标接口。适配器实现目标接口，内部持有被适配对象，并把目标接口调用转换为被适配对象能理解的调用。

## 结构与角色

- Target：客户端期望的接口。
- Adaptee：已有但接口不兼容的类。
- Adapter：实现 Target，包装 Adaptee。
- Client：只调用 Target。

## 适用场景

- 接入旧系统或第三方库。
- 统一多个数据源接口。
- 让外部 API 符合领域层需要。
- 渐进式重构旧代码。

## 不适用场景

- 可以直接修改源接口且成本很低。
- 语义完全不兼容，只是方法名相似。
- 适配器内部需要大量业务补偿，说明边界可能错了。

## 多语言实现

### Java

```java
interface OrderExporter {
    String export(String start, String end);
}

final class LegacyOrderService {
    String queryByRange(String begin, String finish) {
        return "legacy orders";
    }
}

final class LegacyOrderAdapter implements OrderExporter {
    private final LegacyOrderService service;

    LegacyOrderAdapter(LegacyOrderService service) {
        this.service = service;
    }

    public String export(String start, String end) {
        return service.queryByRange(start, end);
    }
}
```

### C++

```cpp
struct Target { virtual int request() = 0; virtual ~Target() = default; };
struct Adaptee { int specificRequest(){ return 1; } };
struct Adapter : Target { Adaptee adaptee; int request() override { return adaptee.specificRequest(); } };
```

### Go

```go
type Target interface{ Request() int }
type Adaptee struct{}
func (Adaptee) SpecificRequest() int { return 1 }
type Adapter struct{ adaptee Adaptee }
func (a Adapter) Request() int { return a.adaptee.SpecificRequest() }
```

### Kotlin

```kotlin
interface Target { fun request(): Int }
class Adaptee { fun specificRequest() = 1 }
class Adapter(private val adaptee: Adaptee) : Target { override fun request() = adaptee.specificRequest() }
```

class CacheClient:
    def get_hot_orders(self, date_prefix: str) -> dict:

class CacheOrderAdapter:

### TypeScript

```ts
interface PaymentPort {
  pay(cents: number): Promise<void>;
}

class ThirdPartyPay {
  charge(amount: string): Promise<void> {
    return Promise.resolve();
  }
}

class PaymentAdapter implements PaymentPort {
  constructor(private readonly adaptee: ThirdPartyPay) {}

  pay(cents: number): Promise<void> {
    return this.adaptee.charge((cents / 100).toFixed(2));
  }
}
```

## 优点

- 不修改旧类即可接入新接口。
- 客户端依赖统一抽象。
- 适合隔离外部系统变化。

## 代价与风险

- 增加一层间接调用。
- 过多适配器会让调用链复杂。
- 语义不匹配时容易隐藏问题。

## 常见误区

- 误区：适配器只是改方法名。
  正解：它还负责语义、参数和数据结构转换。
- 误区：适配器可以弥补任何接口设计错误。
  正解：语义差异太大时应重新设计边界。

## 和其他模式的关系

- 外观模式简化子系统入口，适配器转换接口。
- 代理模式控制访问，适配器解决不兼容。
- 桥接模式预先分离维度，适配器通常用于事后兼容。

## 检查清单

- 客户端期望的 Target 是否清晰？
- Adaptee 是否不应被修改？
- 转换逻辑是否只属于边界层？
- 是否避免把业务规则塞进适配器？
