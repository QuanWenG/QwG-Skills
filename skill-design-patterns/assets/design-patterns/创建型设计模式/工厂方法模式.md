# 工厂方法模式

## 摘要

工厂方法模式定义一个创建对象的接口或抽象方法，让子类决定实例化哪个具体产品。它把“使用产品”和“创建具体产品”的责任分离。

简单工厂通常是一个根据参数 `switch` 创建对象的方法，不属于 GoF 工厂方法模式；它可以是学习工厂思想的起点，但扩展性不同。

## 解决的问题

当客户端直接 `new ConcreteProduct()` 时，客户端会依赖具体类。新增产品或替换产品时，调用方可能需要修改。工厂方法把创建逻辑延迟到 Creator 子类或具体工厂中。

## 核心思想

稳定部分依赖 `Product` 抽象，变化部分由 `Creator.factoryMethod()` 负责。新增产品时，新增具体产品和具体创建者。

原始笔记里从简单工厂过渡到水果工厂的思路是正确的；需要明确：工厂方法不是一个静态 `getFruit(type)`，而是每个具体工厂负责一种具体产品。

## 结构与角色

- Product：产品抽象。
- ConcreteProduct：具体产品。
- Creator：声明工厂方法，也可包含使用产品的模板逻辑。
- ConcreteCreator：实现工厂方法，返回具体产品。

## 适用场景

- 创建对象有复杂逻辑。
- 框架需要让用户扩展产品类型。
- 客户端不应依赖具体产品。
- 产品创建和产品使用需要分离。

## 不适用场景

- 产品类型很少且稳定。
- 创建逻辑只是简单构造，没有隔离价值。
- 需要按产品族创建一组相关对象时，抽象工厂更合适。

## 多语言实现

### Java

```java
interface Button {
    void render();
}

final class WindowsButton implements Button {
    public void render() {}
}

abstract class Dialog {
    protected abstract Button createButton();

    public void show() {
        Button button = createButton();
        button.render();
    }
}

final class WindowsDialog extends Dialog {
    protected Button createButton() {
        return new WindowsButton();
    }
}
```

### C++

```cpp
struct Product { virtual void use() = 0; virtual ~Product() = default; };
struct ConcreteProduct : Product { void use() override {} };
struct Creator { virtual Product* create() = 0; virtual ~Creator() = default; };
struct ConcreteCreator : Creator { Product* create() override { return new ConcreteProduct(); } };
```

### Go

```go
type Product interface{ Use() }
type ConcreteProduct struct{}
func (ConcreteProduct) Use() {}
type Creator interface{ Create() Product }
type ConcreteCreator struct{}
func (ConcreteCreator) Create() Product { return ConcreteProduct{} }
```

### Kotlin

```kotlin
interface Product { fun use() }
class ConcreteProduct : Product { override fun use() {} }
abstract class Creator { abstract fun create(): Product }
class ConcreteCreator : Creator() { override fun create() = ConcreteProduct() }
```

### C#

```csharp
public interface IProduct { void Use(); }
public sealed class Product : IProduct { public void Use() {} }
public abstract class Creator { public abstract IProduct Create(); }
public sealed class ConcreteCreator : Creator { public override IProduct Create() => new Product(); }
```

### Python

```python
from abc import ABC, abstractmethod


class Button(ABC):
    @abstractmethod
    def render(self) -> None:
        ...


class HtmlButton(Button):
    def render(self) -> None:
        pass


class Dialog(ABC):
    @abstractmethod
    def create_button(self) -> Button:
        ...

    def show(self) -> None:
        self.create_button().render()
```

### JavaScript

```js
class Product { use() {} }
class Creator { create() { return new Product(); } }
```

### TypeScript

```ts
interface Transport {
  deliver(): void;
}

class Truck implements Transport {
  deliver(): void {}
}

abstract class Logistics {
  protected abstract createTransport(): Transport;

  planDelivery(): void {
    this.createTransport().deliver();
  }
}

class RoadLogistics extends Logistics {
  protected createTransport(): Transport {
    return new Truck();
  }
}
```

## 优点

- 客户端与具体产品解耦。
- 新增产品符合 OCP。
- 创建逻辑集中在工厂子类。

## 代价与风险

- 类数量增加。
- 每个产品都要配套工厂时可能过重。
- 如果产品族复杂，单个工厂方法不够表达关系。

## 常见误区

- 误区：静态简单工厂就是工厂方法模式。
  正解：简单工厂集中分支，工厂方法通过子类多态创建。
- 误区：工厂方法一定比 `new` 好。
  正解：简单对象直接构造更清晰。

## 和其他模式的关系

- 抽象工厂可以看作一组相关工厂方法。
- 模板方法常在 Creator 中调用工厂方法。
- DIP 让调用方依赖产品抽象。

## 检查清单

- 调用方是否需要避免依赖具体产品？
- 新增产品是否频繁？
- 创建过程是否有业务规则或环境差异？
- 简单工厂是否已经出现扩展压力？
