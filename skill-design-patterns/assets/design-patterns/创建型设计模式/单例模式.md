# 单例模式

## 摘要

单例模式确保一个类在一个进程或容器范围内只有一个实例，并提供统一访问点。它适合管理共享配置、连接池门面、日志器、缓存协调器等“确实需要唯一实例”的对象。

要注意：单例不是全局变量的高级写法。它会引入全局状态、生命周期和测试隔离问题，必须谨慎使用。

## 解决的问题

- 某个对象创建成本高，希望复用。
- 某个资源必须统一协调，例如配置中心客户端。
- 需要在应用范围内共享状态或服务入口。

## 核心思想

把构造器隐藏起来，由类本身、模块系统或容器负责创建并保存唯一实例。线程环境下还要保证并发安全。

原始笔记中的饿汉式、懒汉式、双重检查锁、静态内部类方向正确。需要修正的是：Spring Bean 默认作用域是 singleton，但默认不是懒加载；通常会在容器启动时创建，除非显式配置懒加载。

## 结构与角色

- Singleton：隐藏构造器，保存唯一实例。
- getInstance 或模块导出：提供访问点。
- 客户端：通过访问点获取实例。

## 适用场景

- 配置读取器。
- 日志门面。
- 应用级缓存协调器。
- 线程池、连接池的管理入口。

## 不适用场景

- 普通业务服务，尤其是有用户级状态的对象。
- 需要频繁替换实现的对象。
- 多租户、多上下文中“唯一”的范围不清楚。

## 多语言实现

### Java

```java
public final class AppConfig {
    private AppConfig() {}

    private static class Holder {
        private static final AppConfig INSTANCE = new AppConfig();
    }

    public static AppConfig getInstance() {
        return Holder.INSTANCE;
    }
}
```

### C++

```cpp
class Config { public: static Config& instance(){ static Config c; return c; } private: Config() = default; };
```

### Go

```go
type Config struct{}
var instance = &Config{}
func Instance() *Config { return instance }
```

### Kotlin

```kotlin
object Config { val env = "prod" }
```

### C#

```csharp
public sealed class Config { public static Config Instance { get; } = new Config(); private Config() {} }
```

### Python

```python
class Config:
    def __init__(self) -> None:
        self.env = "prod"


config = Config()
```

### JavaScript

```js
class Config {}
export const config = new Config();
```

### TypeScript

```ts
class Config {
  readonly env = "prod";
}

export const config = new Config();
```

## 优点

- 控制实例数量。
- 统一管理共享资源。
- 避免重复创建昂贵对象。

## 代价与风险

- 全局状态会增加测试难度。
- 隐式依赖让代码可读性下降。
- 并发和生命周期需要谨慎处理。
- 分布式系统中的“唯一”不是单进程单例能保证的。

## 常见误区

- 误区：所有工具类都应该做成单例。
  正解：无状态工具函数可直接用静态方法或纯函数。
- 误区：单例一定线程安全。
  正解：懒加载单例需要正确同步。
- 误区：Spring singleton 等于 JVM 全局唯一。
  正解：它通常是每个 Spring 容器一个实例。

## 和其他模式的关系

- 工厂和抽象工厂有时用单例管理。
- 享元模式共享大量细粒度对象，单例只强调唯一实例。
- 依赖注入容器能替代很多手写单例。

## 检查清单

- 唯一性的范围是进程、容器、线程还是租户？
- 是否包含可变状态？
- 测试时是否容易替换？
- 是否真的比依赖注入更合适？
