# 抽象工厂模式

## 摘要

抽象工厂模式提供一个创建一族相关或相互依赖对象的接口，而无需指定它们的具体类。它关注的是产品族的一致性。

例如同一 UI 风格下的按钮、输入框、弹窗需要配套创建；同一品牌下的手机、手表、平板需要协同。

## 解决的问题

如果系统同时支持 Windows 和 macOS UI，客户端不应分别判断创建 `WindowsButton`、`MacCheckbox`。混用不同产品族会造成风格或协议不一致。抽象工厂把“创建同一族产品”的责任放到一个工厂中。

## 核心思想

抽象工厂声明多个创建方法，每个方法对应一个产品等级；具体工厂负责创建同一产品族中的所有产品。

原始笔记中“按品牌系列横向切割”是很好的理解：抽象工厂关心一族相关产品；工厂方法更多关心一种产品的不同实现。

## 结构与角色

- AbstractFactory：声明创建多个抽象产品的方法。
- ConcreteFactory：创建某个产品族。
- AbstractProduct：产品等级抽象。
- ConcreteProduct：属于某个产品族的具体产品。

## 适用场景

- 需要保证一组对象配套使用。
- 产品族经常新增，例如新增品牌、主题、平台。
- 客户端不应知道具体类。
- 系统需要在运行时切换产品族。

## 不适用场景

- 经常新增产品等级，例如从手机/手表新增汽车。
- 产品之间没有配套关系。
- 只有单一产品类型，工厂方法足够。

## 多语言实现

### Java

```java
interface Button { void paint(); }
interface Checkbox { void paint(); }

final class WinButton implements Button { public void paint() {} }
final class WinCheckbox implements Checkbox { public void paint() {} }

interface GuiFactory {
    Button createButton();
    Checkbox createCheckbox();
}

final class WinFactory implements GuiFactory {
    public Button createButton() { return new WinButton(); }
    public Checkbox createCheckbox() { return new WinCheckbox(); }
}
```

### C++

```cpp
struct Button { virtual void paint() = 0; virtual ~Button() = default; };
struct Checkbox { virtual void paint() = 0; virtual ~Checkbox() = default; };
struct Factory { virtual Button* button() = 0; virtual Checkbox* checkbox() = 0; virtual ~Factory() = default; };
```

### Go

```go

```

### Kotlin


### C#

```csharp

```

### Python

```python
from typing import Protocol


class Button(Protocol):
    def paint(self) -> None: ...


class Checkbox(Protocol):
    def paint(self) -> None: ...


class GuiFactory(Protocol):
    def create_button(self) -> Button: ...
    def create_checkbox(self) -> Checkbox: ...
```

### JavaScript

```js
const factory = { button: () => ({ paint() {} }), checkbox: () => ({ paint() {} }) };
```

### TypeScript

```ts
interface Button { paint(): void }
interface Checkbox { paint(): void }

interface GuiFactory {
  createButton(): Button;
  createCheckbox(): Checkbox;
}

class MacFactory implements GuiFactory {
  createButton(): Button {
    return { paint() {} };
  }

  createCheckbox(): Checkbox {
    return { paint() {} };
  }
}
```

## 优点

- 保证同一产品族一致。
- 客户端与具体产品类解耦。
- 新增产品族符合 OCP。

## 代价与风险

- 新增产品等级会修改所有工厂。
- 抽象层较多。
- 产品族划分错误会导致工厂臃肿。

## 常见误区

- 误区：抽象工厂就是多个简单工厂放一起。
  正解：关键在于一族相关产品的一致创建。
- 误区：抽象工厂总比工厂方法高级。
  正解：二者解决的问题不同。

## 和其他模式的关系

- 抽象工厂内部常由多个工厂方法组成。
- 单例可用于管理无状态工厂实例。
- 建造者关注复杂对象的逐步构建，抽象工厂关注产品族。

## 检查清单

- 是否需要创建一组必须配套的对象？
- 新增的是产品族还是产品等级？
- 客户端是否需要屏蔽具体类？
- 产品族切换是否应该集中管理？
