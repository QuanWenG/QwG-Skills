# 策略模式

## 摘要

策略模式，Strategy，定义一组算法，把每个算法封装起来，并使它们可以互相替换。策略让算法变化独立于使用算法的客户端。

它适合折扣计算、排序规则、路由选择、序列化格式、支付渠道、压缩算法等场景。

## 解决的问题

当一个类中存在大量按类型选择算法的分支时，新增算法会反复修改该类。策略模式把每个算法拆成独立策略，调用方依赖策略接口。

## 核心思想

上下文对象持有策略接口，在运行时注入具体策略。上下文负责流程，策略负责可替换算法。

## 结构与角色

- Strategy：策略接口。
- ConcreteStrategy：具体算法。
- Context：使用策略的上下文。

## 适用场景

- 多个算法可互相替换。
- 算法需要运行时选择。
- 希望消除类型分支。
- 算法细节不应暴露给上下文。

## 不适用场景

- 算法数量少且不会扩展。
- 策略之间共享大量复杂状态。
- 调用方必须理解太多策略差异。

## 多语言实现

### Java

```java
interface DiscountStrategy {
    int apply(int cents);
}

final class VipDiscount implements DiscountStrategy {
    public int apply(int cents) {
        return (int) (cents * 0.8);
    }
}

final class Checkout {
    private final DiscountStrategy strategy;

    Checkout(DiscountStrategy strategy) {
        this.strategy = strategy;
    }

    int total(int cents) {
        return strategy.apply(cents);
    }
}
```

### C++

```cpp
struct Strategy { virtual int apply(int v)=0; virtual ~Strategy()=default; };
struct Context { Strategy& s; int run(int v){ return s.apply(v); } };
```

type Strategy func(int) int

### Python

```python
from collections.abc import Callable

DiscountStrategy = Callable[[int], int]


def vip_discount(cents: int) -> int:
    return int(cents * 0.8)


class Checkout:
    def __init__(self, discount: DiscountStrategy) -> None:
        self._discount = discount

    def total(self, cents: int) -> int:
        return self._discount(cents)
```

### JavaScript

```js
const run = (value, strategy) => strategy(value);
```

### TypeScript

```ts
interface SortStrategy<T> {
  sort(values: T[]): T[];
}

class AscSort implements SortStrategy<number> {
  sort(values: number[]): number[] {
    return [...values].sort((a, b) => a - b);
  }
}

class Sorter<T> {
  constructor(private readonly strategy: SortStrategy<T>) {}
  sort(values: T[]): T[] {
    return this.strategy.sort(values);
  }
}
```

## 优点

- 消除算法分支。
- 算法可独立测试和替换。
- 符合开闭原则。

## 代价与风险

- 策略数量增加。
- 调用方需要选择合适策略。
- 策略接口设计不当会限制算法表达。

## 常见误区

- 误区：策略一定要写成类。
  正解：很多语言中函数就是轻量策略。
- 误区：任何 `if/else` 都要改策略。
  正解：只有稳定出现的算法族才值得抽象。

## 和其他模式的关系

- 状态模式结构相似，但状态会随对象生命周期转换。
- 模板方法用继承扩展步骤，策略用组合替换算法。
- 工厂可根据配置创建策略。

## 检查清单

- 是否存在一组可替换算法？
- 新增算法是否频繁修改上下文？
- 策略接口是否稳定？
- 函数参数是否比完整策略类更简单？
