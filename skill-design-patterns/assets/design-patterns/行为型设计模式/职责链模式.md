# 职责链模式

## 摘要

职责链模式，Chain of Responsibility，把请求沿着一条处理链传递，链上的每个处理者都可以选择处理请求、部分处理后继续传递，或直接交给下一个处理者。

它适合处理步骤可组合、处理者数量或顺序可能变化的场景，例如审批流、过滤器链、中间件链、日志处理、异常处理。

## 解决的问题

当一个请求可能由多个对象处理时，如果调用方用大量 `if/else` 判断谁来处理，会把处理规则和调用逻辑耦合在一起。新增一个处理者或调整顺序都要修改调用方。

职责链让调用方只把请求交给链头，具体由哪个处理者处理由链内部决定。

## 核心思想

每个处理者持有下一个处理者。处理者收到请求后先判断自己能否处理；能处理则处理，不能处理则转发。链可以是“第一个处理者处理后停止”，也可以是“每个处理者都处理一部分后继续”。

## 结构与角色

- Handler：处理者抽象，定义处理方法和下一个处理者。
- ConcreteHandler：具体处理者，实现判断和处理逻辑。
- Client：组装链，并把请求交给链头。

## 适用场景

- 多个对象都有机会处理同一请求。
- 处理者顺序需要灵活调整。
- 希望避免调用方知道所有处理者。
- 请求处理流程类似过滤器、中间件、审批流。

## 不适用场景

- 请求必须被某个处理者处理，但链中没有兜底处理。
- 处理顺序极其关键，却缺少显式配置和测试。
- 处理逻辑之间强依赖共享复杂状态。

## 多语言实现

### Java

```java
abstract class Approver {
    private Approver next;

    Approver setNext(Approver next) {
        this.next = next;
        return next;
    }

    final void approve(int amount) {
        if (canApprove(amount)) {
            doApprove(amount);
            return;
        }
        if (next != null) {
            next.approve(amount);
            return;
        }
        throw new IllegalStateException("no approver");
    }

    protected abstract boolean canApprove(int amount);
    protected abstract void doApprove(int amount);
}

final class Manager extends Approver {
    protected boolean canApprove(int amount) { return amount <= 1000; }
    protected void doApprove(int amount) { System.out.println("manager approved"); }
}

final class Director extends Approver {
    protected boolean canApprove(int amount) { return amount <= 10000; }
    protected void doApprove(int amount) { System.out.println("director approved"); }
}
```

### Python

```python
from __future__ import annotations


class Handler:
    def __init__(self) -> None:
        self._next: Handler | None = None

    def set_next(self, handler: "Handler") -> "Handler":
        self._next = handler
        return handler

    def handle(self, request: dict) -> bool:
        if self._next:
            return self._next.handle(request)
        return False


class AuthHandler(Handler):
    def handle(self, request: dict) -> bool:
        if not request.get("user"):
            return False
        return super().handle(request)
```

### TypeScript

```ts
interface Middleware {
  setNext(next: Middleware): Middleware;
  handle(ctx: { user?: string; body?: unknown }): boolean;
}

abstract class BaseMiddleware implements Middleware {
  private next?: Middleware;

  setNext(next: Middleware): Middleware {
    this.next = next;
    return next;
  }

  handle(ctx: { user?: string; body?: unknown }): boolean {
    return this.next ? this.next.handle(ctx) : true;
  }
}

class AuthMiddleware extends BaseMiddleware {
  handle(ctx: { user?: string }): boolean {
    return Boolean(ctx.user) && super.handle(ctx);
  }
}
```

## 优点

- 调用方和具体处理者解耦。
- 处理顺序和组合可配置。
- 符合开闭原则，新增处理者较容易。

## 代价与风险

- 请求可能无人处理。
- 链太长时调试困难。
- 顺序依赖隐藏后容易出错。

## 常见误区

- 误区：职责链只能有一个处理者最终处理。
  正解：也可以像过滤器链一样每个节点都处理一部分。
- 误区：职责链就是普通循环。
  正解：重点是处理者对象化和调用方解耦。

## 和其他模式的关系

- 装饰器通常包装单个对象，职责链连接多个处理者。
- 中介者集中协调对象，职责链按链式传递请求。
- 命令模式可把请求封装成命令后交给职责链处理。

## 检查清单

- 是否有多个候选处理者？
- 处理顺序是否需要配置？
- 是否有兜底处理者或明确失败策略？
- 链中每个处理者职责是否单一？
