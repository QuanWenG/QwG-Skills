# 解释器模式

## 摘要

解释器模式为某种语言或规则定义文法表示，并提供解释器来解释这些句子。它通常把表达式表示为语法树，然后递归解释每个节点。

它适合小型、稳定、规则明确的语言或表达式，不适合复杂编程语言级别的解析任务。

## 解决的问题

当系统中反复出现一类可组合规则，例如权限表达式、简单计算表达式、搜索过滤条件，可以把规则抽象成表达式树，由解释器统一求值，而不是到处写硬编码判断。

## 核心思想

为文法中的每条规则建立一个表达式类。终结表达式表示不可再拆的符号，非终结表达式组合其他表达式。解释时传入上下文，表达式递归求值。

## 结构与角色

- AbstractExpression：表达式接口。
- TerminalExpression：终结表达式。
- NonTerminalExpression：组合表达式。
- Context：解释所需上下文。
- Client：构建语法树并触发解释。

## 适用场景

- 文法简单稳定。
- 表达式可组合。
- 性能要求不极端。
- 需要把规则对象化，便于测试和组合。

## 不适用场景

- 语法复杂或频繁变化。
- 需要完整词法分析、语法分析、错误恢复。
- 表达式树巨大且性能敏感。
- 已有成熟规则引擎或解析器工具更合适。

## 多语言实现

### Java

```java
import java.util.Map;

interface Expression {
    boolean interpret(Map<String, Boolean> context);
}

final class Variable implements Expression {
    private final String name;

    Variable(String name) {
        this.name = name;
    }

    public boolean interpret(Map<String, Boolean> context) {
        return context.getOrDefault(name, false);
    }
}

final class And implements Expression {
    private final Expression left;
    private final Expression right;

    And(Expression left, Expression right) {
        this.left = left;
        this.right = right;
    }

    public boolean interpret(Map<String, Boolean> context) {
        return left.interpret(context) && right.interpret(context);
    }
}
```

### Python

```python
from dataclasses import dataclass


class Expr:
    def eval(self, ctx: dict[str, bool]) -> bool:
        raise NotImplementedError


@dataclass(frozen=True)
class Var(Expr):
    name: str

    def eval(self, ctx: dict[str, bool]) -> bool:
        return ctx.get(self.name, False)


@dataclass(frozen=True)
class Or(Expr):
    left: Expr
    right: Expr

    def eval(self, ctx: dict[str, bool]) -> bool:
        return self.left.eval(ctx) or self.right.eval(ctx)
```

### TypeScript

```ts
type Context = Record<string, number>;

interface Expr {
  eval(ctx: Context): number;
}

class Num implements Expr {
  constructor(private readonly value: number) {}
  eval(): number { return this.value; }
}

class Add implements Expr {
  constructor(private readonly left: Expr, private readonly right: Expr) {}
  eval(ctx: Context): number {
    return this.left.eval(ctx) + this.right.eval(ctx);
  }
}

class Var implements Expr {
  constructor(private readonly name: string) {}
  eval(ctx: Context): number {
    return ctx[this.name] ?? 0;
  }
}
```

## 优点

- 规则对象化，便于组合和测试。
- 新增简单表达式节点相对容易。
- 语法树结构直观。

## 代价与风险

- 每条语法规则可能都要一个类，类数量多。
- 复杂文法难维护。
- 解析字符串本身通常还需要额外 parser。
- 性能可能不如编译型或表驱动方案。

## 常见误区

- 误区：解释器模式等于写一个完整编译器。
  正解：它适合小型 DSL 或规则树。
- 误区：有表达式求值就必须用解释器模式。
  正解：简单规则用函数、策略或表驱动更轻。
- 误区：解释器包含词法和语法解析全部工作。
  正解：模式重点在表达式对象和解释逻辑，解析器可另行实现。

## 和其他模式的关系

- 组合模式常用于表达语法树。
- 访问者模式可在不改表达式节点的情况下增加新操作。
- 策略模式适合一组互斥算法，解释器适合可组合规则。

## 检查清单

- 文法是否简单稳定？
- 规则是否需要组合成树？
- 是否已有成熟解析器或规则引擎？
- 类数量和性能成本是否可接受？
