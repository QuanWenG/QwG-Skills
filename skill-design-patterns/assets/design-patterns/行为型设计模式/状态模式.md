# 状态模式

## 摘要

状态模式，State，允许对象在内部状态改变时改变它的行为，看起来像改变了对象的类。

它适合对象行为明显依赖状态，且状态转换规则较多的场景，例如订单状态、工单流转、播放器状态、连接状态。

## 解决的问题

如果对象中充满 `if state == ...`，每个行为都要判断状态，新增状态会修改大量分支。状态模式把不同状态下的行为拆到状态类中。

## 核心思想

上下文对象持有当前状态对象。行为调用委托给当前状态。状态对象可以在处理后切换上下文的当前状态。

## 结构与角色

- Context：上下文，持有当前状态。
- State：状态接口。
- ConcreteState：具体状态，实现该状态下的行为和转换。

## 适用场景

- 行为随状态变化明显。
- 状态分支散落在多个方法。
- 状态转换规则复杂。
- 新增状态比新增行为更频繁。

## 不适用场景

- 状态很少且逻辑简单。
- 状态转换需要严格可视化和校验，状态机框架更合适。
- 状态类需要访问太多上下文内部细节。

## 多语言实现

### Java

```java
interface OrderState {
    void pay(Order order);
    void ship(Order order);
}

final class PendingState implements OrderState {
    public void pay(Order order) {
        order.setState(new PaidState());
    }

    public void ship(Order order) {
        throw new IllegalStateException("pay first");
    }
}

final class PaidState implements OrderState {
    public void pay(Order order) {}
    public void ship(Order order) {
        order.setState(new ShippedState());
    }
}

final class ShippedState implements OrderState {
    public void pay(Order order) {}
    public void ship(Order order) {}
}

final class Order {
    private OrderState state = new PendingState();

    void setState(OrderState state) { this.state = state; }
    void pay() { state.pay(this); }
    void ship() { state.ship(this); }
}
```

### Python

```python
class PlayerState:
    def play(self, player: "Player") -> None:
        raise NotImplementedError


class Stopped(PlayerState):
    def play(self, player: "Player") -> None:
        player.state = Playing()


class Playing(PlayerState):
    def play(self, player: "Player") -> None:
        pass


class Player:
    def __init__(self) -> None:
        self.state: PlayerState = Stopped()

    def play(self) -> None:
        self.state.play(self)
```

### TypeScript

```ts
interface ConnectionState {
  send(ctx: Connection, data: string): void;
}

class OpenState implements ConnectionState {
  send(ctx: Connection, data: string): void {}
}

class ClosedState implements ConnectionState {
  send(): void {
    throw new Error("connection closed");
  }
}

class Connection {
  constructor(private state: ConnectionState) {}
  setState(state: ConnectionState): void { this.state = state; }
  send(data: string): void { this.state.send(this, data); }
}
```

## 优点

- 消除大量状态分支。
- 状态行为内聚。
- 新增状态更清晰。

## 代价与风险

- 状态类数量增加。
- 状态转换分散在状态类中时需要文档或测试。
- 状态对象访问上下文过多会产生耦合。

## 常见误区

- 误区：状态模式和策略模式一样。
  正解：结构相似，但状态模式强调状态转换，策略模式强调算法替换。
- 误区：所有枚举状态都要改成状态模式。
  正解：简单状态分支保留枚举更直接。

## 和其他模式的关系

- 策略模式通常由外部选择策略，状态模式通常由内部转换状态。
- 备忘录可保存状态快照。
- 单例可用于无状态的具体状态对象。

## 检查清单

- 是否有大量按状态分支的行为？
- 状态转换规则是否复杂？
- 新增状态是否经常修改多处代码？
- 是否需要状态机表或框架而不是手写状态类？
