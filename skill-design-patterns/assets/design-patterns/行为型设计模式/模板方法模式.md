# 模板方法模式

## 摘要

模板方法模式在父类中定义算法骨架，把某些步骤延迟到子类实现。它适合“流程稳定，局部步骤变化”的场景。

原始笔记中的“流程不变，实现可变”是准确的。示例中打印“倒入杯子”的语句有语法错误，新文档给出修正后的版本。

## 解决的问题

多个类有相同流程，但某些步骤不同。如果每个类都复制完整流程，会产生重复和流程不一致风险。模板方法把固定流程放在父类，变化步骤交给子类。

## 核心思想

父类提供一个模板方法，通常声明为不可重写，例如 Java 的 `final`。模板方法按固定顺序调用基本方法、抽象方法和钩子方法。子类只实现变化步骤。

## 结构与角色

- AbstractClass：定义模板方法和抽象步骤。
- ConcreteClass：实现变化步骤。
- Hook Method：可选钩子，子类可覆盖以影响流程局部行为。

## 适用场景

- 算法流程稳定。
- 多个子类共享大部分流程。
- 框架需要控制执行顺序。
- 希望子类只扩展特定步骤。

## 不适用场景

- 流程本身经常变化。
- 变化维度很多，继承层级会膨胀。
- 需要运行时自由切换算法步骤，此时策略或组合更合适。

## 多语言实现

### Java

```java
abstract class Beverage {
    public final void prepare() {
        boilWater();
        brew();
        pourInCup();
        if (wantsCondiments()) {
            addCondiments();
        }
    }

    private void boilWater() {
        System.out.println("煮水");
    }

    private void pourInCup() {
        System.out.println("倒入杯子");
    }

    protected abstract void brew();
    protected abstract void addCondiments();

    protected boolean wantsCondiments() {
        return true;
    }
}

final class Tea extends Beverage {
    protected void brew() {
        System.out.println("泡茶叶");
    }

    protected void addCondiments() {
        System.out.println("加柠檬");
    }
}
```

### TypeScript

```ts
abstract class ReportExporter {
  export(): string {
    const data = this.load();
    const formatted = this.format(data);
    return this.wrap(formatted);
  }

  protected load(): string[] {
    return ["a", "b"];
  }

  protected abstract format(data: string[]): string;

  protected wrap(content: string): string {
    return content;
  }
}

class CsvExporter extends ReportExporter {
  protected format(data: string[]): string {
    return data.join(",");
  }
}
```

## 优点

- 复用稳定流程。
- 保证执行顺序一致。
- 子类扩展点明确。
- 符合好莱坞原则：不要调用我们，我们会调用你。

## 代价与风险

- 基于继承，耦合父子类。
- 父类变化会影响所有子类。
- 步骤过多时子类理解成本高。

## 常见误区

- 误区：模板方法就是复制一套流程到父类。
  正解：父类应保留稳定骨架，变化点应清晰抽象。
- 误区：所有步骤都应该让子类重写。
  正解：固定步骤应封闭，变化步骤才开放。

## 和其他模式的关系

- 策略模式用组合替代继承，更适合运行时切换。
- 工厂方法常作为模板方法中的一个可变步骤。
- 建造者可封装复杂构建流程，模板方法可固定构建顺序。

## 检查清单

- 流程是否稳定？
- 变化点是否少而清晰？
- 是否需要禁止子类改变执行顺序？
- 组合或策略是否会更灵活？
